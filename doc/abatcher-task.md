# АВМ-Пакетник — контекст задачи

> Файл-памятка для продолжения работы над подпроектом. Не удалять, обновлять по ходу реализации.

## Что это

Новый подпроект наряду с АВМ-Сервис (`coma`) и АВМ-Наладкой — **АВМ-Пакетник**.
Каталоги: `src/abatcher` (Qt-приложение, класс `Abatcher` — главное окно) и `src/avm-autobatch` (упаковка/сборка, `avm-autobatcher.rc`, `package/src/avm-autobatcher.tsv`).

Назначение: автоматизированное выполнение последовательности задач на подключённом по USB модуле — считать текущее состояние (BSI/конфиг/журналы), при необходимости обновить ВПО и конфигурацию до эталонных значений, проверить результат, упаковать все скачанные файлы в ZIP.

Работа идёт в двух режимах: обычный и **"Пробный запуск"** (чекбокс `m_isDry` / `isDry`, уже есть в UI). В пробном режиме шаги, которые могут менять состояние устройства (заливка ВПО, отправка конфигурации) или проверять результат такого изменения, **не выполняются взаправду** — вместо этого пишется предупреждение в лог, а соответствующие пункты 10-12 и 14-16 (см. список ниже) считаются пройденными успешно.

Запись подключена к индикации прогресса через `SyncConnection::setRange`/`setValue` (тот же приём, что в `saveJournal()`), т.к. ~530 КБ пакетами по 64 байта через USB HID может занимать заметное время.
    - **Важно**: команда `C_StartFirmwareUpgrade` (запуск перехода на записанное ВПО) в обычный синхронный запрос-ответ **не укладывается** — устройство перезаписывает себя и перезагружается, пропадая с шины на непредсказуемое время. Отправляется асинхронно (`m_device->async()->writeCommand(...)`, без ожидания прямого ответа — так же делает `FwUploadDialog`), а восстановление связи после неё — самая сложная часть реализации, разбиралась несколько итераций на реальном модуле:
      - Простое ожидание ответа/сигнала `ConnectionManager::reconnectSuccess` без принудительных действий не работало: `ConnectionManager::reconnect()` запускается только реактивно (по ошибке интерфейса/таймауту запроса), и если физическое отключение по USB не всегда доходит до него как явная ошибка, реконнект вообще не стартует.
      - Простой опрос `reqBSI()` в цикле без принудительного переподключения тоже не работал: старый открытый хендл hidapi (`UsbHidPort`) сам по себе не оживает после перезагрузки модуля, его нужно явно закрыть и открыть заново — это и есть `BaseInterface::reconnect()`.
      - Явный вызов `reconnect()` **параллельно** с опросом `reqBSI()` тоже не работал: `DefaultQueryExecutor::reconnectEvent()` (запускается тем же `reconnect()`) деактивирует очередь запросов на время переподключения (`RequestQueue::deactivate()` — входящие запросы в неактивном состоянии игнорируются, см. [request_queue.h](../src/interfaces/include/interfaces/utils/request_queue.h)), реактивирует её только `ConnectionManager::fastCheckBSI()` после того, как его **собственный** внутренний пробный `reqBSI()` (отправленный из `interfaceReconnected()`) получит ответ — параллельные попытки в это окно просто терялись.
      - `Abatcher::startModuleWorker` не задавал `MemKeys::maxErrors`/`maxTimeouts`/`silentInterval` для USB-соединения (оставались на дефолте `BaseSettings` — **0**, см. [base_settings.cpp](../src/interfaces/src/types/base_settings.cpp)), из-за чего единственная случайная помеха на шине сразу после перезагрузки немедленно запускала повторный `reconnect()`/деактивацию очереди. Исправлено — `Abatcher::startModuleWorker` ([abatcher.cpp](../src/abatcher/src/abatcher.cpp)) теперь выставляет `errorCount`/`timeoutCount`/`silentInterval` в 5/5/10000, как и АВМ-Сервис в `AbstractInterfaceDialog` (добавлена константа `MemKeys::maxTimeouts` в [names.h](../src/coma/include/common/names.h), её не было).
      - Настоящая первопричина финальных зависаний — независимый от реконнекта баг в самом `Interface::SyncConnection::reqBSI()`: путь успеха (`count == Device::bsiCountRegs`) никогда не выставлял `m_responseResult = Error::Msg::NoError`, а это поле не сбрасывается в `reset()` и хранит результат **любого** прошлого события `responseError` во всём приложении (постоянное соединение `AsyncConnection::responseError → SyncConnection::responseError`). Во время реконнекта происходит много отмен запросов (`Cancelled`), и это значение "застревало" там до следующего успешного вызова reqBSI — из-за чего `reqBSI()` мог реально успешно дочитать BSI (данные в `m_device->bsi()` обновляются отдельным постоянным соединением `CurrentDevice::updateBSI`, не зависящим от `m_responseResult`), но всё равно возвращал наверх протухший статус ошибки от постороннего события. Остальные `*Sync`-методы этой проблемой не страдают — они либо вычисляют результат сами (по счётчику/размеру данных), либо явно выставляют `NoError` в success-пути. Исправлено: в лямбде успеха `reqBSI()` теперь явно `m_responseResult = Error::Msg::NoError;` рядом с `busy = false;` ([sync_connection.cpp](../src/interfaces/src/conn/sync_connection.cpp)) — это и было настоящей причиной всех предыдущих "зависаний"/"не отозвался".
    - **Итоговая реализация** (проверена на реальном модуле, работает): `ModuleWorker::updateFirmware` после `C_StartFirmwareUpgrade` вызывает `Interface::ConnectionManager::reconnect()` (метод сделан `public`, раньше был приватным) и ждёт сигнал `reconnectSuccess` в цикле с паузой `FwUpgradeRetryIntervalMs` (1 сек) до `FwUpgradeReconnectTimeoutMs` (2 минуты) или отмены пользователем — **не опрашивая `reqBSI()` параллельно**. Заранее неизвестно, сколько секунд займёт переподключение, поэтому вместо счётчика попыток прогресс-бар "Анализ и обновление ВПО" (`prbfwupdate`) на время ожидания переводится в режим "занято" (`PrbFunc::setRange(this, "prbfwupdate", 0)` — QProgressBar с min==max крутится сам, без чисел; попытка показывать `N из 120` смотрелась плохо и осталась такой даже после того, как её обновляли на каждой попытке) — тот же приём, что и в `ReconnectDialog` (АВМ-Сервис) для точно такого же ожидания. По получении `reconnectSuccess` бар возвращается в обычный режим и сразу заполняется (`setRange(1)`/`setValue(1)`). После этого — отдельный прогресс-бар "Чтение Bsi после обновления ВПО" (`prbfwbsi`) для одного вызова `SyncConnection::reqBSI()` (без дополнительных повторов — они были нужны только как обходной путь вокруг бага выше, сейчас не требуются).
    - **Источник эталонной версии ВПО (пункт 9), решение пользователя, 2026-07-03**: для КИВ эталонный файл ВПО (`AVM-KIV_v5_0_22.hex`, версия "5.0-0022") зашит в ресурсы приложения — [firmware.qrc](../src/abatcher/resources/firmware.qrc), путь к файлу `src/abatcher/resources/firmware/kiv/AVM-KIV_v5_0_22.hex`, подключён к исполняемому файлу `avm-autobatcher` (см. [avm-autobatch/CMakeLists.txt](../src/avm-autobatch/CMakeLists.txt)) по тому же принципу, что и общий `images.qrc`. Номер версии для сравнения захардкожен в `moduleWorker.cpp` (`KivReferenceFwVersion`) в упакованном формате `BlockStartupInfo::Fwver`/`StdFunc::VerToStr`. Для остальных типов модулей источник эталона по-прежнему не определён (см. открытые вопросы).
    - Сравнение версий делает только шаги 10-12, если версия в `bsi-old` (шаг 3) не совпадает с эталоном; если версии совпадают, шаги 10-12 сразу считаются пройденными (INFO в лог) без повторного скачивания `bsi`.
    - Логирование ERROR/INFO/WARNING сделано через стандартные Qt-макросы `qInfo()`/`qWarning()`/`qCritical()` — отдельного логгера в проекте нет (см. закрытый вопрос ниже), это тот же подход, что уже использует `FwUploadDialog` (`qCritical()`). В "Пробном запуске" при несовпадении версии, кроме `qWarning()`, показывается ещё и `EMessageBox::warning` — оператор должен увидеть это не только в логе.
    - **Проверено на реальном модуле АВМ-КИВ, 2026-07-03**: полный цикл (сравнение версии → запись ВПО с индикацией прогресса → команда перехода → принудительное переподключение интерфейса → повторное чтение BSI → сравнение и лог результата) успешно отрабатывает целиком, включая настоящее обновление ВПО модуля.

    - **Источник эталонных значений (решение пользователя, 2026-07-03)**: в отличие от ВПО (ресурс приложения), эталонные значения для конфигурационных параметров захардкожены прямо в `moduleWorker.cpp` (`ReferenceConfigParams`, анонимное пространство имён) — по ID: `1035 Tevent_pred=180`, `1036 Tevent_alarm=300`, `1037 Trele_pred=180`, `1038 Trele_alarm=300`. Список не привязан к типу модуля (в отличие от Bac/Startup/ВПО) — параметры проверяются на любом модуле, у которого они присутствуют в конфигурации (`Configuration::contains(id)`); отсутствующие для данного типа модуля ID просто игнорируются.
    - Реализация опирается на существующую инфраструктуру `S2::Configuration`/`S2DataManager`: эталонное значение по ID оборачивается в `S2::Configuration` через `append(id, QString)` — тот же механизм, которым `DataManager::configDataReceive` заполняет `m_defaultConfig` строковыми значениями по умолчанию из XML (типы переменных берутся из `S2ConfigStorage`, см. `S2DataFactory::create(id, QString)`), поэтому сравнение (`DataItem::operator!=`) корректно работает вне зависимости от типа параметра (BYTE/WORD/DWORD/FLOAT/…). `S2::Configuration` нельзя возвращать по значению из функции (копирующий конструктор объявлен `explicit`, что запрещает copy-initialization при `return`) — поэтому эталонная конфигурация собирается через `fillReferenceConfig(S2Configuration&)`, заполняющую уже созданный на вызывающей стороне объект.
    - Принудительная запись (шаг 14) переиспользует уже скачанную и разобранную рабочую конфигурацию (`BoardConfiguration::m_workingConfig`, заполненную на шаге 5 через `requestConfig`/`saveConfig`) — подменяются только значения по нужным ID, затем полный бинарный конфиг (`S2DataManager::getBinaryConfiguration()`) отправляется через `Interface::SyncConnection::writeConfigurationSync` (уже существовал, ранее не был задействован в `ModuleWorker`).
    - Повторное скачивание конфигурации для проверки (шаг 15) сделано через тот же асинхронный путь, что и первое скачивание (`Device::FileProvider::request(S2::FilesEnum::Config, true)` + сигнал `S2DataManager::parseStatus`), но с отдельным разовым (самоотключающимся) подключением, а не повторным использованием `requestConfig()`/`saveConfig()` — те относятся только к самому первому скачиванию (`config-old`). Из-за этого `saveConfig()` пришлось довести до чистого одноразового слота — теперь сама отключается от `parseStatus` при первом срабатывании (раньше подключалась один раз, но никогда явно не отключалась, что было безопасно, пока конфигурация не запрашивалась повторно за сеанс).
    - **Баг №1, найден на реальном модуле, 2026-07-03**: первая реализация читала конфигурацию для проверки (шаг 15) ровно один раз сразу после успешной `writeConfigurationSync` и почти сразу репортовала ERROR "значения параметров не совпадают с эталоном" — при этом на самом деле модуль конфигурацию принял и применил (подтверждено отдельным перечитыванием конфигурации позже, другим запуском пакетника). Причина — модуль применяет только что записанную конфигурацию не мгновенно, чтение сразу после записи попадает на ещё старые значения (тот же класс проблемы, что и с реконнектом после `C_StartFirmwareUpgrade`, см. п. 9-12, только для конфигурации нет отдельного события типа `reconnectSuccess`, на которое можно подписаться). **Исправлено**: `verifyConfigParams()` теперь не проверяет результат один раз, а в цикле повторяет перечитывание конфигурации (через новый `ModuleWorker::rereadConfigBlocking()` — разовый блокирующий запрос конфигурации с собственным таймаутом `ConfigRereadRequestTimeoutMs`) и сравнение с эталоном с паузой `ConfigVerifyRetryIntervalMs` (500 мс) между попытками, пока значения не совпадут или не истечёт общий `ConfigVerifyTimeoutMs`. Прогресс-бар "Проверка конфигурации после обновления" (`prbconfigverify`) на время повторных попыток переводится в режим "занято" — тот же приём, что и в `updateFirmware` при ожидании реконнекта (см. п. 9-12).
    - **Баг №2, найден на реальном модуле сразу после фикса бага №1, 2026-07-03**: пакетник стал репортовать ERROR "Не удалось получить конфигурацию модуля для проверки после обновления" — опять при том, что конфигурация в модуле в действительности обновилась. Причина — в первой версии `rereadConfigBlocking()` соединение с `parseStatus` отключалось только ВНУТРИ самой лямбды при успешном срабатывании; если конкретная попытка не укладывалась в свой таймаут (`ConfigRereadRequestTimeoutMs`), функция возвращала `Error::Msg::Timeout`, но соединение оставалось подключённым. Если реальный ответ от модуля приходил позже (уже после возврата из функции), лямбда обращалась к `done`/`result` — локальным переменным на стеке, которые к этому моменту уже были уничтожены (undefined behavior). Это могло портить состояние следующих попыток непредсказуемым образом и объясняет, почему полный цикл повторов не мог получить корректный ответ, хотя модуль отвечал нормально. **Исправлено**: `disconnect(conn)` теперь вызывается безусловно после цикла ожидания (успех или таймаут), а не только при успехе. Заодно увеличены таймауты на запас: `ConfigRereadRequestTimeoutMs` 3с → 5с, `ConfigVerifyTimeoutMs` 10с → 15с.
    - **Баг №3 (точнее — недостаточные таймауты), найден на реальном модуле после фикса бага №2, 2026-07-03**: с исправленным `disconnect` та же ошибка "Не удалось получить конфигурацию модуля для проверки после обновления" повторилась один в один — т.е. ни на одной из 3 попыток (15 секунд суммарно, 5 секунд на попытку) не был получен вообще никакой ответ на перечитывание конфигурации (`Error::Msg::Timeout` на каждой попытке), а не "значения ещё старые". Значит модуль АВМ-КИВ не отвечает на запросы значительно дольше 15 секунд после записи новой конфигурации. Косвенное подтверждение того, что задержка после записи конфигурации — известная (хоть нигде явно не объяснённая) особенность железа: в `Tune82Verification::setupNFiltrValue()` ([tune82verification.cpp](../src/coma/src/tune/82/tune82verification.cpp)) после своего `writeConfigurationSync` тоже стоит `StdFunc::Wait(1000)` без комментария зачем; в `AbstractTuneDialog::setCurrentsTo()` ([abstracttunedialog.cpp](../src/coma/src/tune/abstracttunedialog.cpp)) есть закомментированная строка `// StdFunc::Wait(5000);` в том же месте — след того, что кто-то раньше уже сталкивался с этим и добавлял ручную паузу. **Исправлено (пока не переподтверждено на железе)**: таймауты увеличены с запасом — `ConfigRereadRequestTimeoutMs` 5с → 10с, `ConfigVerifyTimeoutMs` 15с → 60с. Дополнительно добавлено диагностическое логирование (`qDebug`/`qWarning`/`qInfo` в `rereadConfigBlocking()` и `verifyConfigParams()` — номер попытки, статус, прошедшее время), чтобы при следующей проверке на железе можно было по логу точно увидеть, сколько реально требуется времени, и подобрать таймауты по факту вместо очередной догадки.
    - Конкретное время, которое реально требуется модулю на применение записанной конфигурации, на железе всё ещё не измерено — три попытки подбора таймаутов вслепую (15с → всё ещё мало) показывают, что нужно ориентироваться на лог из следующей проверки, а не гадать дальше.
    - Проверено сборкой (`ninja abatcher avm-autobatcher`) и трижды на реальном модуле (найдены и исправлены баг с гонкой чтения, баг с dangling-соединением и недостаточные таймауты — см. баги №1-3 выше). Полный цикл шагов 13-16 на железе **всё ещё не переподтверждён как работающий целиком** — нужна ещё одна проверка, желательно со внимательным чтением диагностических логов при неудаче.
17. Упаковка всех сохранённых файлов в один ZIP, диалог сохранения архива, итоговое сообщение об успехе/неуспехе всей работы. **Реализовано** (для всего объёма, что скачивается на шагах 1-16). По клику "Начать скачивание" сразу открывается `FileFunc::chooseFileForSave` (см. `ModuleWorker::startDownload`), путь сохраняется в `m_zipFileName`; по завершении конвейера `ModuleWorker::finishDownload` архивирует `m_tempDir` в этот файл через `ZipUtil::CompressDir` и показывает итоговое сообщение. Флаг `m_isCancelled` используется не только для отмены пользователем, но и как индикатор "что-то пошло не так" (по аналогии с `Slices`) — выставляется во всех точках ошибки скачивания/сохранения отдельных файлов, чтобы не показать ложное "Архив сохранён" после сбоя.
    - Образец упаковки: `Slices::createSlice()` + `ZipUtil::CompressDir` (см. пункт 3-6 выше).
    - **В "Пробном запуске" пункты 10-12 и 14-16 считаются пройденными успешно** (несмотря на то что реально не выполнялись).

## Текущее состояние кода (на момент записи, 2026-07-03)

- `Abatcher` ([abatcher.h](../src/abatcher/include/abatcher.h)/[.cpp](../src/abatcher/src/abatcher.cpp)) — главное окно: таблица USB-устройств с автообновлением по таймеру (3 сек), чекбокс "Пробный запуск", кнопка "Запуск". По клику создаётся `ModuleWorker`, окно переключается на него через `QStackedWidget`.
- `ModuleWorker` ([moduleWorker.h](../src/abatcher/include/moduleWorker/moduleWorker.h)/[.cpp](../src/abatcher/src/moduleWorker/moduleWorker.cpp)) — подключается к USB (`connectToUSB`), инициализирует BSI устройства (`Device::CurrentDevice::initBSI`) и загружает XML-конфигурацию модуля (`loadXML`). По кнопке "Начать скачивание" (`startDownload`) сначала спрашивает путь для сохранения ZIP-архива (`FileFunc::chooseFileForSave`), затем последовательно скачивает и сохраняет во временную папку (`QTemporaryDir m_tempDir`): блок Bsi (`saveBsi`), блок BsiExt при наличии (`saveBsiExt`), конфигурацию (`requestConfig`/`saveConfig`) и журналы sys/work/meas (`saveJournals`/`saveJournal`, журнал измерений можно отключить галочкой `m_measJourCheckBox`), с прогресс-барами по каждому шагу и возможностью отмены (`cancelDownload`). По завершении конвейера (`finishDownload`) содержимое временной папки упаковывается в выбранный ZIP через `ZipUtil::CompressDir`, пользователю показывается итоговое сообщение. Кнопка "Назад" эмитит `finishWork()`, по которому `Abatcher` уничтожает `ModuleWorker` и возвращается к списку устройств.
- Реализованы все шаги 1-17. Конвейер в `startDownload` полный, без заглушек: `saveBsi` → `saveBsiExt` → `requestConfig`/`saveConfig` → `saveJournals` → `collectBacBlocks`/`saveBacBlocks` (докачивают настроечные блоки Bac по хардкоду для конкретного типа модуля, складывают в `m_tempDir` как `bac1`, `bac2`, …) → `saveStartup` (для АВМ-КИВ докачивает блок начальных значений `startup`, для остальных типов — no-op) → `checkFirmwareVersion`/`updateFirmware` (шаги 9-12: для АВМ-КИВ сравнивает версию ВПО из уже скачанного `bsi-old` с эталоном из ресурсов и, если нужно и это не "Пробный запуск", обновляет ВПО, сохраняя `bsi` после обновления; для остальных типов — no-op) → `checkConfigParams`/`updateConfigParams`/`verifyConfigParams` (шаги 13-16: сравнивает значения захардкоженных ID конфигурационных параметров с эталоном и, если нужно и это не "Пробный запуск", отправляет эталонные значения в модуль, затем перечитывает конфигурацию и проверяет результат, сохраняя `config`) → `finishDownload`. Шаги 1-12 и 17 целиком проверены на реальном модуле АВМ-КИВ, включая настоящее обновление ВПО. Шаги 13-16 проверены только сборкой (`ninja abatcher avm-autobatcher`) — **на реальном модуле не проверялись**.
